Eagle Business Dashboard — Developer Manual v18.0.10.11.29

This document describes the module architecture, security behavior, data flow, extension points, and validation considerations for Odoo 18.

Version 18.0.10.11.23 — Reactive Operations Orders/Purchase table controls

The Operations Orders and Purchase tables are explicitly component-managed. operations_dashboard.js stores fold state in state.tableSectionsOpen, sort settings in state.tableSort, and exposes sortedOrders/sortedPurchases getters. Each heading binds to sortOperationsTable(); fold clicks use toggleOperationsTable(). Settings persist in local storage. Tables marked data-eagle-managed-controls="1" are skipped by table_tools.js to prevent its DOM-only sort/fold listeners from competing with Owl state.

Module Structure

Python models are in models/. Dashboard controllers are in controllers/. Owl components are in static/src/js/ and templates are in static/src/xml/. Menu and server-side actions are in views/menu.xml.

Dashboard Data Model

The principal RPC model is dashboard.data. Finance data is loaded through methods such as get_finance_dashboard, get_journal_balance, get_journal_transactions, and finance-control methods.

Dashboard Role Groups

The module defines three visible res.groups under the Business Dashboard ir.module.category. group_dashboard_user is the base role; group_dashboard_manager implies User; group_dashboard_admin implies Manager. The res.groups records do not define a sequence field because Odoo 18 does not provide that field on res.groups. The category itself may have a sequence.

Business Dashboard Action Handlers

Dashboard defines createOrder(), createPurchase(), and createPayment(type). These methods are required by the Business Dashboard XML and call Odoo standard window actions through the Owl action service. The payment method sets default_payment_type and default_partner_type before opening account.payment.

This explicit handler contract prevents the Odoo 18 Owl runtime error Invalid handler (expected a function, received: undefined) and prevents the related createPayment is not a function failure.

Payment State Handler

dashboard.data.validate_payment() posts only draft payments. It deliberately does not call action_post() for in_process payments because Odoo 18 treats that state as already posted and awaiting the matching/reconciliation step. The Finance Dashboard XML therefore renders Validate only for draft rows and renders a Match action for in-process rows, which opens the account.payment form via openTransaction().

Date-Range Highlight Refresh

loadAll() loads get_best_worst_day(from_date, to_date) on every dashboard data refresh. This keeps the Selected Period Highs & Lows widget synchronized with the current From/To filter. The date-dependent payload is assigned to state.bestWorstDay. The lighter attractive-pack loader does not fetch this range-dependent value, avoiding duplicate/stale requests.

Sales Trend Graph Architecture

The business dashboard stores the selected trend granularity in state.trendGranularity. The graph controls call onTrendPeriodClick, which delegates to setTrendGranularity. The client then calls dashboard.data.get_trend_data(from_date, to_date, "sale", granularity).

get_trend_data supports day, week, month, quarter, and year grouping. It performs the aggregate query server-side, then generates a complete period sequence and returns zero-valued periods where there were no matching sales records. This avoids exposing hidden records to the browser and keeps aggregation in PostgreSQL.

Owl Template Safety

Finance dashboard templates do not call unsupported JavaScript globals such as String(...) or Object.entries(...) directly. Object-entry preparation is done by the sectionLabelEntries getter and numeric ledger identifiers use normal bracket coercion. The Sales Trend period buttons use a named component handler with a data attribute rather than an inline function expression.

Ledger Security Model

The security configuration model is dashboard.ledger.security. Each bank/cash journal has one security rule with fields journal_id, masked, and approved_user_ids.

The effective visibility function is _ledger_security_rules_for_journals(). It reads the rule and approved-user relation and compares the current Odoo user ID with the approved list.

When masked is true and the current user is not explicitly approved, the journal balance is protected. Configuration access and balance visibility are separate controls.

Cash Flow Aggregate Security

get_finance_widgets() applies ledger visibility per contributing bank/cash journal. For each journal with a default account, the server calculates its opening balance and current balance, then includes those balances in the aggregate only when the current user may view that journal.

Movement totals remain aggregated across all contributing bank/cash journals. Only Opening and Balance are visibility-filtered. Protected numeric amounts are never placed in the RPC payload.

Payload Contract

get_finance_widgets() returns these cash-flow security flags:

cash_balance_masked — at least one contributing journal is protected for the current user.

cash_balance_partial_masked — at least one protected and at least one visible contributing journal exist; numeric Opening and Balance contain only the visible portion.

cash_balance_fully_masked — all contributing journals are protected; Opening and Balance are returned as None.

month_in and month_out remain visible movement totals.

Client Behavior

FinanceDashboard renders a trailing * for partial aggregate masking. For full masking it renders ••••••. The browser never receives the excluded protected amount.

Journal Balance, Print and CSV

Journal Balance still protects individual journal Opening/New Balance values for unauthorized users. Print and CSV continue to use the same server-side journal visibility rule.

Performance

The Cash Flow aggregate is computed server-side. The balance portion is calculated per contributing journal so that journal-level security can be applied before any value is returned to the client.

Extension Guidance

New finance metrics should use server-side aggregation, return only required fields, preserve current-user security semantics, and document any new security-sensitive behavior in both manuals.

Menu Layout

Ledger Balance Security is exposed under the new top-level Settings menu and removed from the Finance dashboard menu. The previous top-level legacy XML ID is retained inactive for upgrade compatibility.

Validation

Validate Python syntax, JavaScript syntax, XML parsing, module manifest consistency, action/menu references, XML event handlers against the owning Owl component methods, absence of invalid res.groups.sequence fields, and ZIP integrity before deployment. Runtime validation should be performed on an Odoo 18 staging database.
