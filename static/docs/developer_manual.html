3. Owl / Frontend Architecture

The backend actions in views/menu.xml use client actions with tags:

advanced_dashboard_tag
finance_dashboard_tag
operations_dashboard_tag

The JavaScript components call the ORM service to invoke dashboard.data methods. Keep server method names and returned dictionary keys synchronized with the Owl templates.

Odoo 18 template rule: avoid complex inline JavaScript expressions in t-on-* handlers. Put non-trivial event logic in named component methods. This prevents Owl template compilation problems and makes code easier to test.

4. Quick Sale Extension

The current Quick Sale implementation calls get_product_options(search) for server-side product lookup and create_quick_sale(partner_id, product_id, qty, price_unit=False) for order creation. Customer and Product inputs are type-to-search controls; selected IDs are passed to the server.

Product search architecture: get_product_options(search) searches the full active, saleable product.product catalog. Each search token is matched against product name, internal reference (default_code), or barcode. The server returns at most 50 matching suggestions to keep the browser responsive; the old fixed 300-product preload has been removed. The frontend debounces product input by 250 ms and ignores stale RPC responses so rapid typing does not overwrite newer results.

When changing the selector UI, preserve the distinction between display text and the selected database ID. Do not trust arbitrary free text as a record ID.

5. Payment Workflow

The dashboard exposes Receive and Send creation actions and a validation action. The server method validate_payment(payment_id) handles payment validation. Keep payment state handling aligned with Odoo 18 rather than older posted-state assumptions.

For outbound payments, use the outbound direction when opening/creating the payment so the Accounting form is a Send transaction.

6. Sales and Purchase Document Progression

The dashboard intentionally does not expose a one-click method that confirms sales/quotations or purchases/RFQs, validates stock transfers, and creates/posts invoices or vendor bills.

There is no complete_business_document() RPC method in this build. Sales and purchase progression remains in Odoo's native document workflows, allowing the application to enforce the normal stock, approval, invoicing and accounting rules at each step.

Extension rule: Do not reintroduce an automatic end-to-end document workflow into the dashboard unless the business process explicitly requires it and each side effect has been designed, authorized and tested independently.

7. Payment State Handling

validate_payment() now keeps the Validate button available for draft and in_process payments. Draft payments call action_post(). An in_process payment is already posted, so the method returns an informational response rather than attempting a second post. Reconciliation/bank matching remains an Odoo Accounting operation.

8. Journal Balance Summary and Collapsible Tables

The Finance dashboard contains a dedicated journal_summary section at the bottom. Finance tables use state.tableOpen with keys for journal, journal summary, invoices, vendor bills, and transactions; all default to false, so tables start folded. The header chevron calls toggleTable(key).

The summary is derived from state.journal_balances returned by get_journal_balance(), mapping opening → Previous, deposit → Deposit, withdraw → Withdraw, change → Change, and closing → New Balance. Deposit/Withdraw values are visible even when Previous/New Balance are masked, matching the printable Journal Balance table.

8.1 Journal Balance Per-Journal Expansion

Each row in the Finance Dashboard Journal Balance table is an independent collapsible record. The top-level table remains controlled by state.tableOpen.journal; per-journal expansion is controlled by state.journalRowsOpen.

Clicking a journal row calls toggleJournalRow(journalId). The child transaction rows are derived from filteredTransactions by matching the server-supplied journal_id. This keeps the inline drill-down aligned with the dashboard date and partner filters and avoids a separate RPC request for every expansion.

The expanded list uses the existing openTransaction() navigation for each payment. Deposit and Withdraw totals are calculated from the matching transaction rows. The server method get_finance_dashboard() includes journal_id on each payment transaction so the client can map transactions to journal rows reliably.

9. Ledger Balance Security

The standalone administrator menu is Business Dashboard → Finance Dashboard → Settings → Ledger Balance Security, or use the Ledger Security button in the Finance Dashboard header. It calls the sync server action first so every bank/cash journal has a configuration row before opening the list/form view.

dashboard.ledger.security stores one rule per bank/cash journal with journal_id, masked, and Many2many approved_user_ids. The model is admin-only through security/ir.model.access.csv; the configuration check accepts the module Dashboard Admin group and Odoo's system administrator group.

The admin Settings modal calls get_config() and set_config() on the security model. The enforcement point is dashboard.data.get_journal_balance(): it resolves the current user’s Dashboard Admin status or journal-specific approval and returns None for protected opening/closing balances. The numeric change remains in the response for all users. This masking must remain server-side so a browser cannot retrieve the hidden amount by modifying JavaScript.

When any journal is masked for the current user, Previous/Current aggregate totals are also masked in the frontend to prevent a total-value side channel. The Finance widget method also masks aggregate Cash Balance/Cash Flow values and adds cash_balance_masked; openCashBalance() refuses to open the unrestricted Bank & Cash journal-items action while the aggregate is protected. Change totals remain visible.

9. Frequently Bought Together

The product-bundle logic is implemented by get_product_bundles(). Frontend rendering should receive product names/identifiers rather than attempting to render raw JavaScript objects. If the UI shows [object Object], inspect the returned payload and the template expression first.

11. Snapshot Route

/dashboard/snapshot/<token>

The controller looks up dashboard.snapshot.link, checks expiry, loads the stored snapshot JSON, and renders the snapshot QWeb template. The route is public so a generated snapshot can be opened without logging in; therefore avoid putting sensitive information into a snapshot.

12. Adding a New Dashboard KPI

  1. Add the calculation to the appropriate dashboard.data method.
  2. Return a stable JSON-serializable value/key.
  3. Read the value into the corresponding Owl component state.
  4. Add the KPI card to the relevant XML template.
  5. Add any click handler as a named JavaScript method.
  6. If it opens an Odoo list, use open_dynamic_action() with a validated model/domain.
  7. Run Python, XML and JavaScript syntax checks before upgrading.

13. Security and Permissions

The module relies on Odoo model access rules and the permissions of the current user. Do not use sudo() merely to make dashboard numbers appear for users who lack access. If a feature intentionally needs elevated access, document the reason and minimize the elevated scope.

Any new model requires an appropriate entry in security/ir.model.access.csv.

14. Upgrade / Deployment Procedure

  1. Back up the database and filestore.
  2. Replace the module directory with the new version.
  3. Restart Odoo.
  4. Upgrade the module from Apps or with the Odoo command-line upgrade mechanism.
  5. Hard-refresh the browser if frontend assets changed.
  6. Check the Odoo server log for Python, XML, asset or Owl errors.

15.1 XML Load Order Fix

The Ledger Balance Security tree/form views and the action_ledger_balance_security window action are defined before any <menuitem> references to that action. Odoo resolves a menu action XML ID while processing the menu item, so referencing an action declared later in the same XML file can cause External ID not found during module upgrade.

15. Validation Checklist

  • Python: python -m compileall
  • XML: parse every XML file and ensure all referenced IDs exist.
  • JavaScript: node --check on modified JS files.
  • ZIP: verify archive integrity before deployment.
  • Runtime: test installation/upgrade on a staging Odoo 18 database before production.
Important: Static checks cannot replace a real Odoo 18 runtime/database test. Always perform the final upgrade and functional test on staging.

16. Recommended Extension Practices

  • Keep server methods small and return explicit structures.
  • Use ORM searches with appropriate domains and limits.
  • Avoid N+1 ORM queries in dashboard loops; batch-read related records where practical.
  • Escape/display values through Owl/QWeb normally; do not inject untrusted HTML.
  • Keep frontend state names synchronized across Business, Finance and Operations dashboards.
  • Document every new RPC method and persistent model.
  • Do not store large image binaries in PostgreSQL when external object storage plus URL fields is the intended architecture.

15.2 Root Dashboard Navigation Handlers

The root Dashboard component renders several table links that call openPartner() and openTransaction(). These methods must be defined on the root component itself; defining them only on FinanceDashboard is insufficient because Owl binds this to the component that owns the template.

The current implementation defines openPartner(id) and openTransaction(id) alongside openOrder() and openPurchase(). This prevents client-side errors such as v44.openPartner is not a function and v66.openTransaction is not a function.

This developer manual is based on the supplied module source. It describes the implementation present in the supplied build and should be updated when the module architecture changes.

Journal Balance — Per-Journal Transactions

Each journal row in both Journal Balance tables is a collapsible record. toggleJournalRow(journalId) toggles state.journalRowsOpen and, on first expansion, asynchronously calls dashboard.data.get_journal_transactions(journal_id, from_date, to_date). Results are cached in journalRowTransactions and loading state in journalRowLoading. This removes dependence on the general finance transaction list and ensures expansion works even when the general list is filtered or lacks a journal identifier.

loadAll() clears the per-journal expansion/cache state after date/filter refresh. The server response is still subject to the existing get_journal_transactions() semantics and limit; the UI does not fabricate transaction rows.

Finance print report: line-item header alignment

The Finance Dashboard print renderer aligns the line-item headers consistently: Product is left-aligned, while Qty, Rate, Disc%, Tax, and Total are right-aligned. The Owl template no longer calls the global Number() constructor directly; transaction amounts use the component formatAmount() helper to avoid Odoo Owl template context errors such as ctx.Number is not a function.

Journal transaction validation

When Journal Balance or Journal Balance Summary is expanded, draft and in-process payment transactions display the same Validate button available in the main Transactions table. The button calls the dashboard payment-validation method, then refreshes the finance data. Paid transactions do not show the button.

Payment Validate Handler — Root Dashboard

The business dashboard transaction table and finance journal drill-down templates may invoke validatePayment(id). The root Dashboard component now implements this handler as well as FinanceDashboard. Both call dashboard.data.validate_payment, show the backend message for already-posted in-process payments, refresh data, and reset state.validatingPaymentId in a finally block.

Journal Transaction Source States

get_journal_transactions returns draft, in-process, and paid payments for the selected journal/date range so the journal drill-down can present the same payment-state behavior as the main Transactions table.

Frontend navigation compatibility: The root Business Dashboard component implements the same partner and payment transaction navigation handlers used by its templates, so links in Business Dashboard tables open the corresponding Odoo records without openPartner is not a function or openTransaction is not a function errors.
