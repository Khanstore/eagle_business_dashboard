Eagle Business Dashboard — Developer Manual v1.0.33

This document describes module structure, runtime flow, security, performance design, and extension considerations for Odoo 18.

Module Structure

Python server methods are in models/dashboard.py. Owl dashboard components are in static/src/js/ and templates in static/src/xml/. Menus and actions are in views/menu.xml.

Dashboard Components

Dashboard implements the main Business Dashboard. FinanceDashboard implements Finance views. OperationsDashboard implements the default Operation Dashboard.

Quick Sale Architecture v1.0.33

Quick Sale is implemented by static/src/js/quick_sale_dialog.js as an isolated DOM dialog. It is intentionally not part of the large reactive Owl tree used by the dashboards.

Typing flow

DOM input event
  → local query value
  → clear existing debounce timer
  → increment search sequence
  → 350 ms debounce
  → ORM RPC dashboard.data.get_product_options
  → sequence check
  → render small result list in the dialog DOM
  → click/keyboard selection
  → store product ID locally
  → create_quick_sale RPC

No product-search keystroke changes the parent dashboard's Owl state. A successful search therefore does not trigger a full dashboard render.

Search results

The client caches recent query results in a bounded Map. Results are limited by the server to 30 active, saleable products. Matching fields are name, internal reference, and barcode.

Stale requests

searchSeq invalidates previous requests. A response is ignored when its sequence does not match the latest query or when the dialog has been closed.

Cleanup

Closing the dialog clears the debounce timer, invalidates pending searches, removes the keydown listener, and removes the dialog DOM node.

Server Quick Sale Search

dashboard.data.get_product_options rejects queries shorter than two characters. It uses a bounded search_read and returns only fields needed by the dialog. create_quick_sale additionally validates that the selected product exists, is active, and is saleable.

Partial Aggregate Visibility

get_finance_widgets() retains the existing default-account cash calculation. Protected default-account contributors are excluded from the aggregate returned to unauthorized users. When both protected and unprotected contributing accounts exist, cash_balance_partial is true and the UI appends *. When no unprotected contributor remains, cash_balance_masked is true. cash_balance_drilldown_allowed is false whenever protected contributors exist so the aggregate card cannot open an unrestricted bank/cash journal-items view.

Ledger Balance Security

Ledger security is enforced server-side. A protected journal's Previous/New Balance fields are removed from unauthorized responses. Deposit, Withdraw, and Change remain available. Administrator membership grants configuration access but does not automatically reveal a protected balance.

Performance

Dashboard data is bounded and heavy analytics are deferred. Generic table tools are presentation-only. Quick Sale is intentionally isolated from that reactive tree to prevent typing from traversing the full dashboard template.

Maintenance

Changes to behavior, configuration, workflow, security, or architecture must update this Developer Manual and the User Manual. Validate Python syntax, JavaScript syntax, XML parsing, manifest consistency, and ZIP integrity before deployment.

Testing Boundary

Static validation confirms syntax and structure. Runtime behavior must be verified on an Odoo 18 staging database, including Quick Sale typing, search latency, product selection, order creation, and dashboard refresh.

Quick Sale Architecture v1.0.33

The Quick Sale dialog is rendered outside the parent Owl tree. Partner and product inputs use local DOM state, bounded ORM RPCs, request sequence guards, and dedicated dropdown rendering. Partner search calls dashboard.data.get_partner_options; product search calls dashboard.data.get_product_options. The server remains authoritative for product validity and order creation.

Quick Sale action controls: Cancel and Create Order are created programmatically with isolated styling so both remain visible and clickable regardless of generic Odoo button styling.

Quick Sale actions

The primary Create Order action and Cancel action are rendered inside the visible Quick Sale form body. They do not depend on the Odoo modal footer. The primary action is available after a valid product selection and remains visible during search and validation states.

Operation Dashboard document actions

openSalesPrintWizard and openPurchasePrintWizard open scope-specific print modals. The sales scope renders Sales Orders and Quotations; the purchases scope renders Purchase Orders and RFQs. Scope flags control which line details are emitted. The top print action retains the all-sections mode.

Operation Dashboard transactions

createPayment(type) opens the standard account.payment form with the appropriate default_payment_type and default_partner_type context. No automatic posting is performed.

Payment form direction theme v1.0.33

The standard account.payment form is tinted light red for Send/Outbound and light green for Receive/Inbound. The primary implementation is CSS-based and reacts directly to the checked payment_type radio, with a minimal JavaScript fallback for DOM variants. This does not change payment or accounting behavior.

Transaction CSV export v1.0.35

The Operation Dashboard transaction CSV includes separate Receive and Send columns. Receive contains inbound payment amounts and Send contains outbound payment amounts. Transaction print tables use the same separate columns. The exporter no longer combines the two directions into a single Amount column.

Transaction columns v1.0.35

Transaction tables and transaction CSV/print outputs use separate Receive and Send columns. Receive contains inbound payment amounts; Send contains outbound payment amounts. A transaction has a value in the applicable direction column and zero/blank in the other direction, according to the source data.
