This document describes the module architecture, security behavior, data flow, extension points, and validation considerations for Odoo 18.

Module Structure

Python models are in models/. Dashboard controllers are in controllers/. Owl components are in static/src/js/ and templates are in static/src/xml/. Menu and server-side actions are in views/menu.xml.

Dashboard Data Model

The principal RPC model is dashboard.data. Finance data is loaded through methods such as get_finance_dashboard, get_journal_balance, get_journal_transactions, and finance-control methods.

Dashboard Role Groups

The module defines three visible res.groups under the Business Dashboard ir.module.category. group_dashboard_user is the base role; group_dashboard_manager implies User; group_dashboard_admin implies Manager. The res.groups records do not define a sequence field because Odoo 18 does not provide that field on res.groups. The category itself may have a sequence.

Ledger Security Model

The security configuration model is dashboard.ledger.security. Each bank/cash journal has one security rule with fields journal_id, masked, and approved_user_ids.

The effective visibility function is _ledger_security_rules_for_journals(). It reads the rule and approved-user relation and compares the current Odoo user ID with the approved list.

When masked is true and the current user is not explicitly approved, the journal balance is protected. Configuration access and balance visibility are separate controls.

Cash Flow Aggregate Security

get_finance_widgets() applies ledger visibility per contributing bank/cash journal. For each journal with a default account, the server calculates its opening balance and current balance, then includes those balances in the aggregate only when the current user may view that journal.

Movement totals remain aggregated across all contributing bank/cash journals. Only Opening and Balance are visibility-filtered. Protected numeric amounts are never placed in the RPC payload.

Payload Contract

get_finance_widgets() returns these cash-flow security flags:

cash_balance_masked — at least one contributing journal is protected for the current user.

cash_balance_partial_masked — at least one protected and at least one visible contributing journal exist; numeric Opening and Balance contain only the visible portion.

cash_balance_fully_masked — all contributing journals are protected; Opening and Balance are returned as None.

month_in and month_out remain visible movement totals.

Journal Balance, Print and CSV

Journal Balance still protects individual journal Opening/New Balance values for unauthorized users. Print and CSV continue to use the same server-side journal visibility rule.

Performance

The Cash Flow aggregate is computed server-side. The balance portion is calculated per contributing journal so that journal-level security can be applied before any value is returned to the client.

Extension Guidance

New finance metrics should use server-side aggregation, return only required fields, preserve current-user security semantics, and document any new security-sensitive behavior in both manuals.

Validation

Validate Python syntax, JavaScript syntax, XML parsing, module manifest consistency, action/menu references, absence of invalid res.groups.sequence fields, and ZIP integrity before deployment. Runtime validation should be performed on an Odoo 18 staging database.

Sales Trend Graph

The Business Dashboard renders Sales Trend as a dependency-free SVG graph. The UI stores the selected trendGranularity in component state and requests dashboard.data.get_trend_data(from_date, to_date, 'sale', granularity). Supported values are day, week, month, quarter, and year. The server groups sale_order rows using PostgreSQL DATE_TRUNC. The client computes a responsive Y-axis, grid ticks, points, line, area fill, and collision-aware X-axis labels without external chart libraries.
